The security advisor reports a warning for `public.rls_auto_enable()`: it is a `SECURITY DEFINER` function and is executable by `PUBLIC`, `anon`, and `authenticated`. A read-only privilege query confirmed those grants. The function body and intended use must be reviewed, then execution should be restricted if public invocation is not intentional. **No privilege change was made.**

### Application database integration

The current application expects a PostgreSQL connection string in server-side `DATABASE_URL` and uses `pg.Pool`. `src/api/database.ts` runs `SELECT 1` for its database health check. The documented SSL controls are:

- `DATABASE_URL` — PostgreSQL connection string (server-side secret)
- `DATABASE_SSL=require` — enables TLS in the current pool implementation
- `DATABASE_SSL_REJECT_UNAUTHORIZED=true` — keeps certificate verification enabled
- `DATABASE_POOL_MAX` — pool size

The Supabase project URL or publishable/anon key is **not** a replacement for `DATABASE_URL`. The application currently has no Supabase Auth/Data API integration in its inspected runtime path. Supabase can serve as its PostgreSQL database through a compatible PostgreSQL connection string, but that connection has not been proven from the Render runtime.

## 6. Security and reliability observations

### Existing foundations

- Server-side provider calls and environment-based secrets.
- Express security headers, production CSP and HTTPS redirect policy.
- Password hashing, HttpOnly session cookies, CSRF checks and Zod input validation.
- Request IDs, request logging and redaction helper.
- Owner-scoped conversation routes.
- Admin endpoint checks authenticated admin role.
- Terminal shell execution is deliberately disabled.
- Offline Learning pack-verification foundations use signatures and hashes.

### Priority security gaps

1. Review and restrict the public `SECURITY DEFINER` function in Supabase after inspecting its body and intended callers.
2. Confirm all application tables are created with appropriate ownership constraints and, if exposed through Supabase Data API, RLS policies. The current live public schema has no tables.
3. Add granular backend-enforced staff permissions; UI-only hiding is insufficient.
4. Review provider credential storage/encryption and ensure secret values are never returned to clients.
5. Review API-wide and feature-specific rate limits, especially process-local counters that do not coordinate across multiple instances.
6. Keep shell execution disabled until a real isolated sandbox with resource, filesystem and network boundaries exists.
7. Add idempotent conversation writes/recovery and reliable sync before declaring multi-device persistence production-ready.

No production security setting, database privilege, migration, secret or user data was changed during this audit.

## 8. Prioritized 12-hour execution backlog

This order is dependency-driven. A “12-hour mission” is a timebox, not permission to bypass release gates.

### P0 — Establish a trustworthy foundation
1. Preserve current main and all divergent branches; review local changes before any local checkout/merge.
2. Reconcile the migration set with the empty Supabase database; review the public function warning.
3. Confirm Render environment-variable presence without revealing values and verify application-to-Supabase connectivity.
4. Establish migration backup/restore and a staging verification path. Request approval before any production migration.

### P1 — Complete the core web/cloud path
1. Consolidate provider adapters behind a stable interface; add only providers with documented, testable APIs.
2. Make provider configuration/credential handling secure and admin-authorized.
3. Complete model discovery, capability verification, routing policy, cancellation and observability.
4. Make conversation writes idempotent and recoverable; finish edit/delete/regenerate/history synchronization.
5. Gate image, file, voice and video features accurately when providers are not configured.

### P2 — Make Offline Hub honest and useful
1. Complete the model metadata schema and license/source display.
2. Separate “catalogue result”, “downloaded”, “integrity verified”, “installed” and “runtime compatible” states.
3. Finish Android download lifecycle/recovery and local model registry.
4. Verify llama.cpp model load/generation on a supported Android device.
5. Keep browser inference limited to models actually supported by WebGPU/WebLLM; never label unknown compatibility as ready.

### P3 — Terminal and administration
1. Keep shell disabled; improve read-only terminal UX and error handling.
2. Design a sandbox interface before implementing any command execution.
3. Define granular staff roles/permissions and enforce them in every admin API.
4. Audit provider secrets, admin changes, user actions and staff lifecycle.

### P4 — Cross-platform and experience
1. Complete EN/Dari, then add Pashto and Arabic dictionaries and RTL validation.
2. Improve responsive shell, accessibility and reduced-motion behavior.
3. Choose a desktop architecture (for example, a supported desktop shell) before Windows/macOS/Linux packaging.
4. Evaluate iOS local inference separately under App Store and device memory constraints.

### P5 — Verification and release
Only after explicit authorization: run type checks, tests, builds, safe staging migrations, Android device tests, provider smoke tests and deployment verification. No production migration or deployment should be performed without separate explicit approval.
